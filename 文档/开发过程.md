# 开发过程记录

> 本文面向接手或评审本项目的人:交代技术选型、开发顺序、每个关键取舍的理由,
> 以及明确「做了什么 / 没做什么」。与《项目介绍》互补,那篇讲"是什么",这篇讲"为什么"。

## 一、任务与约束

任务:在微信小程序开发者工具中,复刻一张示例图(设备上行速率监控卡片)的可交互流量图;
允许 mock 数据与开源组件;代码进入 git 仓库,至少两次提交(一次初始化、一次最终版)。

## 二、技术栈与选型理由

| 项 | 选择 | 理由 | 备选为何不选 |
|---|---|---|---|
| 框架 | 微信小程序原生(无 Taro/uni-app) | 任务目标是复刻示例图,单页 demo,引入跨端框架纯属负担 | 跨端框架:构建链复杂,收益为零 |
| 图表 | echarts-for-weixin(ec-canvas,内含 ECharts 5.3.3 UMD 构建) | 示例图的 tooltip 样式、虚线准线、面积填充即 ECharts 风格(推断);触摸交互组件层已封装好 | wx-charts:年久失修、交互弱;F2(f2-canvas):移动端 H5 语境适配要自己做;原生 canvas 手绘:准线/tooltip/命中检测全要重造轮子 |
| 渲染器 | webview(canvas 2d 模式) | ec-canvas 的 canvas 2d 面向 webview 渲染器;Skyline 下兼容性官方未背书(待验证项,未冒进) | skyline:模板默认开启,但为图表稳定性主动退回 |
| 验证 | node + ECharts SSR(无 npm 依赖) | 开发环境没有开发者工具 CLI,视觉问题必须有一个不进 IDE 的可复算验证手段 | jest/最小图测试框架:为 145 个点的 demo 引入测试体系不成比例 |

## 三、大致框架与开发顺序

开发按「可验证的最小闭环」推进,六个决策点依次是:

1. **读图拆解**:把示例图翻译成元素清单(标题行/指标行/折线面积/虚线准线/tooltip 三行/45° 轴标签/曲线分段形状),
   并发现数学关系 `水位 = 速率 ÷ 带宽`(示例 tooltip 中 5.28 G ÷ 10 G = 52.8%),据此确定指标全部由数据推导。
2. **选型与取件**:GitHub `git clone` 被网络重置,但 `raw.githubusercontent.com` 可达,故 curl 逐文件拉取 ec-canvas 六个文件,`node --check` 验证完整性。
3. **渲染器切换**:app.json `skyline → webview`(理由见上表)。
4. **mock 数据生成器**:`基线分段函数 + 种子伪随机噪声`。基线按示例图形状写分段
   (静默/陡升/指数衰减/谷底/锚点插值爬升/骤降/高位平台/归零),mulberry32 种子保证确定性。
   **纯函数、不依赖 wx** 是刻意设计:node 可直接跑,数据形态先用数值断言验证(峰谷位置、点数、水位),
   再谈画图。
5. **图表配置**:`utils/trafficOption.js` 逐项对照示例图写 option(轴刻度、旋转、tooltip formatter、渐变面积)。
6. **验证体系**:模拟器截图暴露裁剪问题后,建立 `scripts/verify-render.js`(ECharts SSR 渲染 → 解析每个
   `<text>` 包围盒 → 断言零越界 + 刻度内容),让「文字会不会被裁」从猜变成可复算。

提交切分为:初始化模板 → 图表功能 → 裁剪修复 → 刻度空档修复 → 文档与工程化。功能提交保持
「每个提交都是可运行状态」。

## 四、做了什么(全部产出)

- ec-canvas 组件接入(canvas 2d + 触摸事件转发,组件零修改);
- 首页监控卡片 UI(自定义导航保留,标题/指标行/图表布局);
- 确定性 mock 数据生成器(145 点,分段基线 + 噪声,水位推导);
- 完整 ECharts 配置(旋转轴标签、轴刻度策略、tooltip、渐变面积、准线);
- SSR 渲染验证脚本(含越界断言与内容断言,exit code 可用于 CI);
- 三轮模拟器实测问题修复:Y 轴名裁剪、X 轴首标签裁剪、指标行换行、首二刻度空档。

## 五、没做什么,以及为什么

| 没做 | 理由 |
|---|---|
| 真实数据接口 | 任务明确允许 mock;接口层留了清晰替换点(见《项目介绍》兼容性一节) |
| ECharts 定制裁剪(减小 ~1MB 体积) | 主包 2MB 限制内放得下;定制构建引入打包链,与 demo 定位不符。若上线,建议按需 build 一次 |
| 真机测试 | 本环境无真机;SSR(SVG 渲染器)与真机(canvas 2d)共享布局逻辑但字体测量可能有细微差异,已列为待复核项 |
| tooltip HTML 富文本(蓝色圆点标记) | 小程序 canvas 模式下 HTML 标记可靠性存疑(推断,未逐版本实测),采用稳定的文本「●」方案 |
| 深色模式 / 国际化 / 单元测试框架 | demo 范围外;SSR 脚本已承担核心回归职责,测试框架待多页面时再引入 |
| Skyline 渲染器适配 | 生态组件(canvas 2d 依赖)未背书,强行适配风险大于收益 |

## 六、关键取舍的详细记录(踩坑即文档)

1. **`containLabel: true` 不计旋转标签宽度**(实测):X 轴标签旋转 45° 后,
   `containLabel` 只按未旋转宽度预留空间,首标签仍会向左越界。
   解法:`grid.left` 手动放大到能容纳旋转后横向分量(~55px)。
2. **`showMinLabel: true` 的连带抑制**(实测):强制显示首标签后,与其旋转包围盒
   几乎重叠的第二个刻度会被 ECharts 自动隐藏,造成「首二标签间隔翻倍」的空档。
   解法:放大刻度间隔(80min → 120min),让第二个自然标签走出首标签重叠区;
   三种绕法(函数式 interval 等)均实测过,该方案最优。
3. **Skyline → webview**(决策):图表稳定性优先;若未来整体迁移 Skyline,
   需要上游 ec-canvas 支持或改用 skyline 兼容的图表方案,这是独立专题。
4. **utils 用 CommonJS 而非 ESM**(决策):小程序两种都支持,但 CommonJS 能被
   node 直接 require,是 SSR 验证体系的前提。页面侧用 require,ec-canvas 组件保持
   上游 ESM 原样不动。
5. **node ≥ 21 跑 echarts 构建版会崩溃**(实测):构建版按 `navigator` 等全局对象
   判断环境,新版 node 自带 `navigator` 会被误判为浏览器而引用 `window`。
   解法:require 之前 `delete globalThis.navigator`,让它走内置 node 分支。
6. **SSR 后进程不退出**(实测):chart 有动画定时器,验证脚本必须 `chart.dispose()`
   (或 `process.exit`)否则 node 挂住。
7. **模板真实 appid 混入公开历史**(事后被 GitHub 告警发现):appid 在模板初始提交即存在,
   仅在最后一次提交替换是不够的——GitHub Secret Scanning 会扫描**全部历史**并邮件告警
   ("Tencent WeChat API App ID · project.config.json#L2")。处置:`git filter-branch`
   全历史替换为 `touristappid` 后 force-push。教训:公开发布前必须对全部历史做
   `git grep <敏感串> $(git rev-list --all)`,只查工作区/最新提交等于没查。

## 七、给后续开发者的建议路线

1. 接真实数据:新增 `utils/api.js`,产出与 `buildTrafficSeries()` 同构的数组;
   保留 mock 作为接口异常时的降级与演示数据。
2. 多设备回归:把 `scripts/verify-render.js` 的宽高参数化(目前 330×360,即 iPhone6 基准),
   对常见尺寸各跑一遍;有条件时补真机截图比对。
3. 性能化:数据点增多后给 series 加 `sampling: 'lttb'`;tooltip 高频刷新可加 `throttle`。
4. 若图表页面增多:考虑把 option 构造参数化(带宽/MAC 作为入参),抽取公共轴样式。
